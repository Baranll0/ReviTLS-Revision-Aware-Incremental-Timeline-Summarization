# ReviTLS: Revision-Aware Incremental Timeline Summarization

ReviTLS is an incremental timeline summarization (TLS) framework for news streams in which earlier claims are later corrected or retracted. Events are mutable states with a lifecycle (`ACTIVE`, `REVISED`, `RETRACTED`) and an append-only supersession log. It builds on two LLM-based TLS paradigms: incremental clustering (**LLM-TLS**, Hu et al., ACL 2024) and iterative 5W1H self-questioning (**CHRONOS**, Wu et al., NAACL 2025).

> **Status.** The code and paper were revised on 2026-11-23. Results from earlier commits (including the tables in `docs/history_log.md` and `outputs/scie_results/`) were produced by a previous implementation and **must not be cited for the current code**. Current results are written to `outputs/final/` by the procedure in [`docs/RUN_ON_5080.md`](docs/RUN_ON_5080.md), and the paper in `paper/main.tex` reads every number from them.

## How it works

1. **Extraction (7B).** Each article becomes a claim: summary, event date, entities, key facts, `who/what/where/why/how` slots, and an LLM revision flag.
2. **Revision candidates.** A claim is a candidate if a lexicon cue fires, the LLM flags it, or a structural probe finds a similar cross-date state that reports a different value for the same measure (or a date within 7 days).
3. **Conditional dual-horizon gate.** Routine claims match same-day states only (top-3 compared in one call); candidates use a 90-day horizon with bi-encoder + cross-encoder reranking.
4. **Chronological replay (14B).** Candidates are verified in a replay of the stream in publication order. Evidence only comes from articles published up to that point; a unit test enforces this.
5. **Quote-gated retraction.** `RETRACTED` is accepted only if the verifier returns a verbatim quote found in the supplied evidence; otherwise the status falls back to `REVISED`.
6. **Timeline.** Retracted states are dropped; the rest are scored with `w_c log(1+c) + w_r [REVISED] + (w_s/6)(filled slots)`, one state per date.

See [`docs/architecture.md`](docs/architecture.md) for details and known limitations.

## Evaluation

| What | Script | Output |
| --- | --- | --- |
| Held-out revision suite (110 generated chains, fictional entities, negative controls) | `scripts/run_heldout_suite.py` | `outputs/final/heldout.json` |
| T17 / Crisis full corpus, per-reference averaging, ablations | `scripts/run_fullcorpus.py` | `outputs/final/summary.json` |

| Paper tables and number macros | `scripts/make_paper_tables.py` | `paper/generated/` |

Metrics: Date-F1, Concat/Align ROUGE (our reimplementation, **not** `tilse`), and for revision handling RRA (resolution), SFLR (stale-fact leakage), negative-control pass rate, and false-retraction rate, at state and timeline level. Protocol for the transition audit: [`docs/transition_audit_protocol.md`](docs/transition_audit_protocol.md).

## Setup

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install torch --index-url https://download.pytorch.org/whl/cu128   # GPU machine only
pip install -e ".[dev,gpu,eval]"
pytest
```

Unit tests need no GPU or LLM server. A model-free plumbing check of the held-out pipeline:

```powershell
python scripts/run_heldout_suite.py --dry-run --limit-cases 12 --output outputs/dry/smoke.json --fresh
```

Real runs need [Ollama](https://ollama.com/) serving `qwen2.5:7b-instruct-q4_K_M` and `qwen2.5:14b-instruct-q4_K_M` and the corpora (`scripts/download_datasets.ps1`, `scripts/prepare_datasets.py`). Full instructions: [`docs/RUN_ON_5080.md`](docs/RUN_ON_5080.md).


## Known limitations

Routine decisions are cached in Phase 1 and not recomputed after a revision. AR/Concat ROUGE are not `tilse`. CHRONOS is an implementation-limited local adaptation. The held-out suite is generated by the system's author and isolates chains in time. See the paper's limitations section.
